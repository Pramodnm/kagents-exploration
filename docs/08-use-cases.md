# 08 · Common use cases and how this stack fits them

Each row is an agent pattern that people commonly build, with how kagent and Agent
Substrate handle it, what this exploration verified, and where the gap is. "Fit" is a
judgment based on the evidence in chapters 04 to 06.

| # | Use case | Fit | What this work showed | Gap |
|---|---|---|---|---|
| 1 | Conversational assistant, declarative | Strong | Agent Ready, Session with transcript memory across turns | Per-turn token overhead (about 3k+) |
| 2 | Assistant that calls MCP tools | Strong | MCP `kagent-api` tools used by the sandbox agent | Tool calls outside the binding observed (F10) |
| 3 | Framework agent (Microsoft Agent Framework, Go) behind A2A | Adequate | Three personas served over AG-UI inside one image; A2A invokes complete | Persona differences not visible in-cluster (F6); build friction (chapter 04) |
| 4 | Multi-agent: one agent delegates to a specialist | Adequate | Documented subagent tree (one level) | Not built in this work |
| 5 | Code execution for a model's generated code | Weak for untrusted code | Notebook and Python run in a sandbox; memory limited | Raw-IP egress open (F1); CPU limit unconfirmed (F4) |
| 6 | Data analysis in a notebook | Adequate | Jupyter image built and used; nbconvert output read back | Image must be built and pinned in advance (no runtime installs) |
| 7 | Long-running research or incident investigation | Adequate | Suspend and restore observed in atelet logs | Long idle periods and cost of snapshots not measured |
| 8 | Scheduled or background jobs | Not tested | Scheduled runs exist in the API reference | Not built here |
| 9 | Human approval before a tool runs | Not tested | HITL extension advertised on the agent card | Not exercised in this work |
| 10 | Customer-facing chat with per-user data | Weak by default | Session model is separate from Kubernetes RBAC | Default `insecure` mode; identity must be configured |
| 11 | Coding agent that edits a repo in a sandbox | Adequate for trusted repos | Upload, exec, and download work; file tools exist | Egress control (F1) before running untrusted dependencies |
| 12 | Model gateway with multiple providers | Adequate | ModelConfig per provider; OpenAI-compatible gateway verified | Provider list differs by harness (chapter 02 of the docs) |
| 13 | Agent that must call internal APIs with its own identity | Adequate | Egress credential injection and Actor token documented; not built | Per-agent identity path not exercised |
| 14 | Replacing a large fleet of always-on agent pods | Strong in principle | Many Actors multiplexed onto a pool (documented); single-node tests only | No scale test in this work |

## Patterns that worked, and why

**Declarative first, BYO when the framework demands it.** The three-line Agent path
(Harness, AgentTemplate, Agent) covered the conversational case with no code. The BYO path
was needed only for a framework that owned its own loop. That is the right order.

**One trusted tool surface per agent.** The sandbox agent worked because its tool list was
short. Agents that bind many tools will call the ones you did not intend, so keep the
list short.

**Pinned images everywhere.** Harnesses, SandboxTemplates, and the guest image all require
digests. This is friction on the first build and a benefit on every later one, because a
revision reproduces exactly.

## Patterns that did not work, and why

**Shell entrypoints in distroless images.** A launcher that calls `/bin/sh` fails. Use a
binary entrypoint.

**Two processes in one BYO image.** Starting a server as a child and then `exec`-ing the
agent loses the race under Substrate. Use one process that binds its listener first.

**Secrets in Harness env.** Harness env is literal-only in this release. Use ModelConfig
and gateway injection for every key.

**Relying on the prompt for policy.** The sandbox agent's prompt forbade installs and
extra templates. The platform did not enforce the network rule, and the model still made a
tool call outside its binding. Enforce with the template, the tool binding, and the
network, not the prompt.

## Choosing between a sandbox and a BYO agent

| If the code is | Use | Why |
|---|---|---|
| Written by you, reviewed, and trusted | Either | BYO gives your framework; sandbox gives scratch space |
| Generated by a model at run time | Sandbox, with an outer network control | The sandbox runs it; egress must be blocked outside kagent until F1 is fixed |
| A full agent loop you already have | BYO | Fixed A2A contract, managed Sessions |
| A one-off script | Sandbox | Create, run, delete; under a second to create |
